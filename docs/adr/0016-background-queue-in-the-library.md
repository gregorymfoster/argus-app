# 0016: The background Queue lives in the Library, and Suggestions are never applied

Greg wants to import a shoot, walk away for a couple of hours, and come back to edits waiting for him: two or three Suggestions per Photo (sliders, crop and straighten) and, after he edits one Photo by hand, matched Suggestions for the rest of the Shoot. He stays the final reviewer.

We keep that work as rows in the Library's `jobs` table and run it with one worker thread per process (the app, or `argus serve`, or `argus work`). The alternatives were an in-memory queue, which loses hours of model time on every quit or crash, and a separate daemon, which is one more thing to install, keep alive and update on an unsigned app. Rows in SQLite (WAL) survive a quit, travel with the portable Library (ADR 0009), and can be filled by any thread or tool through `enqueue_job` without knowing who runs them. A job left `running` is simply queued again on the next start, so every job must be safe to run twice; Suggestions are, because a run replaces the Photo's open Suggestions of the same flavour.

Suggestions are stored in their own `suggestions` table as whole Recipes and never touch `recipe_versions` until the person accepts one, which writes a Version in its own Batch. That keeps the Recipe history honest (only what the person chose) and means the Agent and the Queue can be as bold as they like. "Apply to the rest" makes the Hero Photo's style a new Look (saved, assigned to nobody) and puts each other Photo under it only through accepted Suggestions, with per-Photo Corrections and crop.

The worker rests between jobs by Compute level and boosts itself to Full when macOS reports the Mac idle for ten minutes (`ioreg` HIDIdleTime), on top of ADR 0007's throttling inside each model request. Two processes on one Library would each run a worker; claiming a job is one transaction, so they never run the same job, but they would double the load. The app and `argus serve` aren't meant to run on the same Library at once.

## Addendum (2026-10-18): background work waits for the charger

Greg asked for background AI to need the Mac plugged in, after a long Gentle queue ran on battery. On battery (macOS `pmset -g batt`, read at most every 30 s; `ARGUS_POWER=battery|ac` fakes it) the worker only claims jobs at the open Photo's priority (100), so Loupe and Edit stay quick while culls, Suggestions and analysis wait. The idle and overnight boosts to Full need AC too. `set_queue` takes `run_on_battery` (Settings › AI › "Run background AI on battery", off by default) and `run_anyway` (the Background work panel's "Run anyway", which lasts until the Mac is next plugged in); `queue_status` reports `on_battery` and `battery_paused`. A queue that is merely held keeps its jobs queued, so nothing is lost and plugging in resumes it. `retry_failed` re-queues failed jobs (newest of each dedupe key, none already queued) for when a model was briefly missing.
