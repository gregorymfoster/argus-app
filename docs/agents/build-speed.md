# Build and test speed

Greg (2026-10-18): always keep caching and build-graph ideas in mind. Add an idea here with an estimated saving when you spot one; move it to "Done" when it lands.

## Health

Every long step runs under `scripts/progress` (see its header). `just status` prints one line per step: state, elapsed, done/total, ETA and the last output line; a run whose wrapper stopped heart-beating shows as `DEAD?`. Logs are `out/logs/NAME.log`, timings of the last good run `out/logs/durations.json` (they drive the ETA when a script prints no `::progress` lines). Default stall limit is 15 min without output; bench gets 60, release 30, app-e2e 20.

## How caching works here

Three layers, each doing one job. Cargo is the per-crate build DAG: it rebuilds only crates whose inputs changed, as long as the target folder survives (Greg's checkout keeps `target/` and `app/target/` between runs). sccache sits under it in cloud sessions, where every container starts with an empty target folder. `scripts/cached` sits above it: a content-hash cache for whole steps (test runs, clippy, the frontend build, the release's `npm ci`). It hashes the step's inputs (git-visible files under `--in`, names and sizes under `--stat`, the output of `--key` commands such as `rustc -vV`) and skips the step when the hash matches its last passing run. `just check` with nothing Rust-side changed takes about 1 s instead of ~40 s, so docs-only lands and re-runs after a failed push are nearly free. `ARGUS_NO_CACHE=1` forces everything.

Why not moon, Turborepo, Nx or Bazel (2026-10-18): the repo is two Rust crates plus the app and one Vite package, and cargo already does per-crate build caching better than a generic runner could. What a task runner adds on top is step-level skip-if-unchanged, which `scripts/cached` gives in one stdlib Python file that runs the same on the Mac and in the cloud with nothing to install. Test results can't be cached finer than per test binary without Bazel-style per-test dependency tracking, which no light tool offers for Rust. Revisit if the repo grows more packages or a shared remote cache between machines starts to matter.

## Ideas, biggest first

- **Where `just check` spends its time** (measured 2026-10-22 on the 4-core cloud box, other agents building alongside, so +-10%). After a one-line engine edit: fmt 0.5 s, clippy 4 s, compiling the test binaries ~8 s (the engine crate is most of it; deps and the linker are not: Rust 1.99 already links with lld on Linux), tests ~29 s. The tests are CPU-bound: the integration binary is 81 s of tests run one at a time, 27 s on 4 threads. Its slowest: `denoise::denoise_amount_queues_the_base_and_renders_blend_it` 9 s, `compute::gentle_backgrounds_and_duty_cycles_ollama_then_lets_it_go` 9 s (all sleep, so it costs a thread, not CPU), the `jobs::` tests 1-3.5 s each.
- **Denoise base save and load in parallel** (product code, saves ~4 s of CPU per `just check` and time for the person). The test's 9 s is mostly `denoise::save` (1.8 s, one thread deflating a 254 MB 16-bit base) twice and `load` (1.0 s inflating it) twice; the fake model and the demosaic take 0.5 s. Deflating row bands as separate streams on rayon, or storing it unpacked, would cut that ~4x. Needs a base format bump (`VERSION`).
- **cargo-nextest** (estimated a few seconds more off the test step on 4 cores, more on the Mac; untimed). One process per test, so the 9 s sleeping compute test and the denoise test stop holding back their binary, and `env_lock` would no longer be needed. Costs a tool to install on the Mac and in cloud setup; `scripts/test-parallel` gets the binary-level half of it with nothing to install.
- **Cloud disk.** The container has ~40 GB, and a `fast` target folder is ~5 GB (2.7 GB of it incremental), ~2 GB more for each extra feature set (e.g. after a `-p argus-engine` build). Several agents in worktrees with their own `CARGO_TARGET_DIR` filled it on 2026-10-22, and tests then failed with "database or disk is full". Delete a worktree's target folder when its agent is done.
- **sccache misses in worktrees.** Hits need the same target path, so agents building in their own worktree target folders fill the shared cache without reusing it. If that becomes common, point their `CARGO_TARGET_DIR` at one shared path per worktree slot.
- **App e2e on an optimised engine.** `app-e2e` builds the app in debug, so the engine and image crates run at opt-level 0. `[profile.dev.package."*"] opt-level = 2` in `app/Cargo.toml` would make decode and render in the e2e much faster for a slower cold build; untimed (needs WebKit).
- **sccache on the Mac** (asked of the Mac thread 2026-10-20). Only cold builds gain (after a dependency bump or a wiped target, ~5 min today); incremental Argus crates pass through it.
- **Orchestration, not compiling, is most of a release's wall time** (2026-10-20). On Greg's Mac a warm release is quick: `just check` 0:19, `just mac-e2e` 1:04, the release build 0:42-1:00 when only Argus crates changed (4:53 after a dependency change at gentle, 5:43 cold), plus ~35 s of DMG bundling. What makes a release take an hour is the agent loop: each step is a separate command the driving thread polls at most every 5 minutes, and anything that needs Greg (a gh login, the publish OK) waits for him. `just release-candidate` removes the step waits; the rest is people.

## Tried, didn't pay

- **App on the workspace's target dir and `fast` profile** (2026-10-18). `CARGO_TARGET_DIR=../target npx tauri build --no-bundle -- --profile fast` with a matching `[profile.fast]` in `app/Cargo.toml` took 7:30 cold against 3:36 for today's debug build, and reused nothing: the app's dependency features differ, so cargo hashes rawler, image and the engine differently (the root target already holds three rawler builds: engine alone, workspace tests, cli). Optimised code also compiles slower. Not worth it unless the app joins the root workspace with unified features.

## Done

- **Test binaries side by side** (2026-10-22). `scripts/test-parallel` builds with `cargo test --no-run`, then runs every test binary cargo reports plus the doc tests at once, each one's output printed whole when it ends. Test step 35.0 s to 29.1 s, three alternating runs each on the cloud box: the engine's unit tests (7 s) now overlap the integration tests (27 s).
- **Denoise model test on two tiles** (2026-10-22). The unit test binary's long pole ran the real model on 2x2 tiles of a 300x260 gradient (~11 s); one row of two tiles keeps the seam blend on model output and runs in parallel: ~7 s, of which 2.8 s is loading the model.
- **No `-p argus-engine`** (2026-10-22). On its own the engine resolves fewer dependency features than the workspace (serde `rc`, libc `extra_traits`, syn `full`, chrono `serde`, tracing `attributes`), so `cargo test -p argus-engine` built a second copy of ~90 crates: 281 s, and ~2 GB of disk. From the repo root without `-p`, cargo selects every member and reuses `just check`'s build. `just bless` and the skills say so. `resolver.feature-unification = "workspace"` would fix it for good but is still nightly-only in cargo 1.99.
- **`just check` copies the sample RAWs and turns on sccache** (2026-10-22, `scripts/cloud-ensure`). The SessionStart hook didn't run in a projects session: the container resumes a snapshot from the hook's first run (2026-10-20, before `/mnt/project-files` was mounted), so it had no RAWs and no sccache, and a land silently skipped the goldens. Agent worktrees start without RAWs too. A RAWless run still warns.
- **A flaky keywords test** (2026-10-22). `keywords::search_finds_photos_by_keywords_captions_and_names_and_albums_keep_up` sorted Photo ids and took them for capture order, but Import's workers finish in any order: 2 of 24 parallel runs failed under load. It now keeps `list_photos`' capture order.
- **One Rust everywhere** (2026-10-20). `rust-toolchain.toml` pins the channel the Mac runs (1.99), so cloud clippy catches what the Mac's does; v0.1.4 lost a round to five lints only the Mac's newer clippy knew. Bump it when the Mac updates. The first build after a bump is cold (and sccache misses once).
- **`just release-candidate X.Y.Z`** (2026-10-20) runs `just check`, then `just mac-e2e` beside `release-local --build-only` (separate target folders; the UI's npm install and Vite build run first through `scripts/cached` so neither repeats them), as one job. `just ship` adds the publish and the installer dry run: Greg's one "ship it" covers both, which removes the ~15 min wait for a second OK. `--build-only` no longer needs `gh` logged in (v0.1.4's build stopped on a lapsed login before compiling anything); the published-version checks then run at `--publish-only`.
- `just mac-e2e` builds at gentle priority (utility QoS + nice 10, all cores) instead of background QoS with `-j 2`, which pinned it to the 4 efficiency cores (Greg chose this 2026-10-20).
- `app-e2e`, `app-e2e-quick` and `mac-e2e` skip `npm install` when the lockfile is unchanged (`scripts/cached`).
- **Release builds** (2026-10-18). Measured on the 4-core cloud container, `cargo build --release -p argus-cli`, no sccache: thin LTO took 463 s cold and 182 s after an engine change; no LTO with 16 codegen units 330 s and 65 s; the `fast` settings (no LTO, 256 codegen units, incremental) 6 s after an engine change. `just speed`, two runs each, `fast` against thin LTO: decode 83-118 ms vs 90-142, Edit slider 41-42 vs 52, previews 197-200 vs 222-224 ms/photo, Import the same. So `[profile.release]` in both `Cargo.toml` and `app/Cargo.toml` now uses the `fast` settings. (Both were already above the cloud baseline's 27 ms slider before this change.)
- **Release priority** (2026-10-18). `taskpolicy -b` (background QoS) pins a process to the efficiency cores on Apple Silicon (4 of the M4 Max's 16), which made most of the ~25 min. `ARGUS_BUILD_PRIORITY` in `scripts/release/local.sh`: `gentle` (default) is utility QoS plus `nice -n 10`, which uses the performance cores and still yields to Greg's apps; `full` drops all limits; `background` is the old mode. Not yet timed on the Mac.
- `scripts/cached` skips the prototype's Vite build in `tauri build` (release and app-e2e) when `prototype/` is unchanged, and the release's `npm ci` when the app's lockfile is unchanged.
- `fast` Cargo profile for tests and throwaway binaries (one-file edit rebuild ~5 s vs 5 min on `--release`).
- `cloud-setup.sh` warms the `fast` build and clippy in the background at session start, so the first `just check` mostly reuses it.
- `app-e2e-quick` for iterating on the first part of the e2e.
- `app-e2e-setup` downloads the cargo-quickinstall prebuilt tauri-driver (seconds) and only compiles it if the download fails (was 1-2 min).
- `cargo build -p argus-cli` (render, speed, bench, live, mac-e2e) reuses what `just check` built: the cli's normal deps carry the same tokio and rmcp features as its tests. Before, the feature mismatch re-hashed libc, tokio and ~15 crates above them, a 3:55 rebuild after a cold `just check` (2026-10-18).
- Clippy runs on `--profile fast`, so it shares build scripts and proc-macros with the test build: cold clippy 0:40 instead of 2:07 (2026-10-18).
- Cloud sessions use sccache with its cache in `/mnt/project-files/cache/sccache` (3 GB cap), set up by `cloud-setup.sh` in the container's own `~/.cargo/config.toml`. Measured 2026-10-18 on a fresh target dir: cold `cargo test --workspace --profile fast --no-run` 416 s without it, 466 s while filling the cache, 130 s with a warm cache (100% hits; the remaining time is the incremental workspace crates and linking). Hits need the same target path, so a test in another directory misses everything. The cache is ~500 MB of small files on a network mount: deleting it took over 10 minutes, so don't clear it casually. Greg's Mac doesn't use it.
- Engine integration tests are one binary (`engine/tests/main.rs`, `--test engine`, each old file a module, so `golden::` filters one file). `just check` measured 2026-10-18 on the cloud container, before and after, one run each: no-op 20 s to 12 s, after a one-file engine edit 32 s to 19 s; same 153 tests. Tests now share a process: anything setting an env var takes `crate::env_lock()`, and a test re-running its own binary names itself with the module path (`library_safety::kill_child_writer`).
